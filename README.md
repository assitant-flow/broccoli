# Broccoli

> 一个面向「多项目、多需求、持续协作」的云端 AI 开发平台。

## 一句话定位

Broccoli 让你把一整个项目的多个需求一次性交给 AI，它会自动、有序地完成它们；你只需要在一个统一的界面里查看所有项目和任务的进展，而不必在多个终端之间来回切换。它会记住你的项目上下文、决策和偏好，越用越懂你。

## 产品形态与定位

- **形态**：云端 SaaS 平台。用户通过浏览器提交需求、查看仪表盘、review 与合并产出，无需在本地维护任何常驻进程。
- **目标用户（MVP）**：个人开发者——同时维护多个项目、希望把成串的需求托付给 AI 而不是全程陪跑的人。
- **执行引擎**：基于成熟 agent 框架 + Claude Code Agent SDK 构建，Broccoli 的核心价值不在于重新造一个 coding agent，而在于其上的**编排、监控与记忆层**。

## 背景：我们在解决什么问题

当前使用 AI 辅助开发（无论是 CLI 工具还是 IDE 插件）时，存在三个被普遍接受、但实际上很不合理的事实：

### 痛点一：需求是串行的，人是被动的

一个项目往往有多个需求：修一个 bug、加一个功能、重构一个模块。而现在的 AI 工作流是：

```
提出需求 1 → 等 AI 完成 → 人工确认 → 提出需求 2 → 等 AI 完成 → …
```

用户被迫成为整个流水线中的「调度器」——每个需求完成后，必须人工回来输入或讨论下一个需求。AI 明明可以持续工作，人却把它用成了「一问一答」。**用户的真正角色应该是提出目标，而不是驱动每一步。**

### 痛点二：多任务 = 多终端 = 眼睛的灾难

当多个项目、多个需求并行推进时，用户不得不开多个 terminal 窗口/标签，靠手动切换来查看每个 AI 任务的状态：

- 任务是跑完了、卡住了，还是在等输入？
- 有没有哪个任务失败了需要介入？
- 每个项目的进度到哪了？

信息分散在各个终端里，没有全局视图，**用户的心智负担随项目数量线性增长**。而且切换查看本身就在打断用户正在做的事。

### 痛点三：AI 是健忘的

每次新会话、每个新需求，AI 都从零开始了解你的项目：技术栈、目录结构、编码规范、之前做过的决策。用户被迫反复交代背景，或者接受 AI 因为缺乏上下文而产出偏离预期的结果。

## Broccoli 的答案

### 1. 需求队列（Requirement Queue）：从「对话」升级为「任务编排」

用户可以把一个项目的多个需求一次性提交，Broccoli 将它们组织为队列，自动逐个执行：

- **顺序执行**：默认按序处理，每个需求完成后自动开始下一个，用户无需介入。
- **依赖感知**：可以声明需求之间的依赖关系（如「先重构，再加功能」），Broccoli 按依赖图调度。
- **需要时才找人**：只有当 AI 遇到真正需要决策的问题（如方案分歧、需要确认破坏性变更）时，才会通知用户；其余时间自主推进。
- **随时插入**：新需求可以随时加入队列，不影响正在执行的任务。

### 2. 统一仪表盘（Dashboard）：一个界面，看清所有项目

替代「N 个终端来回切」的是一屏全局视图：

- **项目级视图**：每个项目当前在做什么、队列中还有哪些需求待执行。
- **任务级视图**：单个需求当前的执行状态（进行中 / 等待确认 / 失败 / 完成）、AI 的实时输出、产出的 diff。
- **异常优先**：需要人工介入的任务（等待确认、执行失败）被置顶提醒，用户可以只处理这些，其余放着不管。
- **介入与放权**：用户可以随时打开某个任务深入讨论、修正方向，也可以直接批准让 AI 继续。

### 3. 记忆系统（Memory）：越用越懂你的项目

Broccoli 为每个项目（以及每个用户）维护持久化的记忆：

- **项目记忆**：技术栈、架构约定、目录结构、编码规范、构建与测试方式——AI 在执行任何需求前自动加载，无需重复交代。
- **决策记忆**：历史需求中做过的技术决策（「我们不用 X，因为 Y」），避免 AI 反复推翻已有结论。
- **偏好记忆**：用户个人的沟通与代码偏好（如 commit 风格、是否要写测试）。
- **需求间传承**：队列中前一个需求的产出和结论，自动成为后续需求的上下文，多个需求不再是彼此孤立的会话；任务结束即生成记忆提案并立即注入下一个任务，无需等待确认。
- **可拥有、可迁移**：记忆沉淀属于用户资产，未来可导出为仓库约定文件（如 CLAUDE.md），不锁死在平台内。

## 典型使用场景

```
早上 9:00  用户把「项目 A」的 5 个需求（修 bug、加登录、写测试…）
          和「项目 B」的 2 个需求分别提交到各自队列，然后去做别的事。

上午 10:30 邮件提醒：项目 A 的第 2 个需求需要确认数据库选型。
          用户点开链接，花 2 分钟给出决定，任务继续。

下午 2:00  用户打开仪表盘：项目 A 已完成 3/5，项目 B 已完成 2/2。
          逐个 review 产出的 diff，按序合并；顺手批量确认当日记忆提案。

全程没有切换过一次终端，没有手动「喂」过一个新需求。
```

## 与现有方式的对比

| | 传统终端 + AI CLI | 云端 agent 平台（Devin、Factory、后台 agent 类） | Broccoli |
|---|---|---|---|
| 多需求推进 | 每个需求完成后需人工输入下一个 | 以单任务为主，成串需求的编排较弱 | 队列自动调度，一次提交全部 |
| 多项目并行 | 多终端窗口手动切换 | 面向团队的任务看板 | 个人多项目的统一仪表盘 |
| 人工介入时机 | 全程在线陪跑 | 任务内交互 | 只在需要决策时被邮件通知 |
| 上下文 | 每次会话从零开始 | 平台内会话级为主 | 持久化记忆自动加载 |
| 需求间上下文 | 无 | 一般无 | 前序需求结论自动传承（提案即注入） |
| 记忆资产 | 仓库内约定文件（CLAUDE.md 等） | 平台内锁定 | 确认式沉淀，可导出带走 |
| 定价 | 订阅制为主 | 团队级订阅 / 按量计费，单价偏高 | BYO key，只为沙箱算力付成本价 |

需要说明：**「队列 + 仪表盘 + 后台自主执行」在云端 agent 产品中已渐成标配**，Broccoli 不以此为差异化，而是聚焦三点：

1. **个人开发者的多项目聚焦**——竞品多面向团队与订阅制，Broccoli 面向「一人维护一串项目」的真实工作形态，BYO key 让成本贴近实际用量。
2. **需求队列的编排深度**——串行队列、堆叠 PR、需求间上下文传承、失败策略，把「一天托付 5 个需求」这条路径打磨到极致，而非做泛化的单任务 agent。
3. **记忆的可拥有与可迁移**——确认式记忆沉淀，未来可导出为仓库约定文件；越用越懂你的资产属于用户，而不是平台的锁定手段。

## 设计原则

1. **人是目标设定者和决策者，不是调度器。** 一切设计都在减少「必须人在场」的时刻。
2. **默认自主，介入有门。** AI 自主推进，但用户始终能查看、暂停、纠正任何任务。
3. **信息找人，而不是人找信息。** 状态变化主动呈现，异常优先，而不是等用户去查。
4. **记忆是资产。** 用户与项目的每一次协作都应沉淀为可复用的上下文。

## MVP 架构决策

以下是已确定的关键决策；带优先级的完整 MVP 功能清单见 **[docs/mvp-scope.md](docs/mvp-scope.md)**。

| 决策点 | 结论 |
|---|---|
| 代码执行位置 | **云端沙箱**：用户授权 Git 托管平台（如 GitHub），仓库 clone 至云端容器，agent 在容器内执行；架构上预留本地 runner 接入点 |
| 需求来源 | **两者结合**：以 Web 界面手动输入自然语言需求为主，GitHub Issues 同步为辅 |
| 调度策略 | **项目间并行、项目内串行**：不同仓库的任务天然独立可并行；同一项目内需求队列严格按序执行，前序产出作为后续上下文 |
| AI 引擎 | 基于成熟 agent 框架 + Claude Code Agent SDK，Broccoli 专注编排、监控与记忆层 |
| 目标用户 | 个人开发者（多项目并行、成串需求托付） |
| 产出交付 | **MVP 仅支持 GitHub repo 项目**：走「分支 + PR」（堆叠策略：需求 N 基于需求 N-1 的分支，按序合并；失败 / 挂起跳过时 base 回退至最后成功分支）；沙箱文件项目（无 Git）降为 P1 |
| 执行并发与挂起 | 单用户默认 2 个沙箱容器并发（仅计执行中），超出排队；**「等待确认」立即保存会话快照并释放容器、不占并发槽位**，快照默认保留 24h（可配置），超时转「已挂起」 |
| 确认问答协议 | 结构化预设选项 + 允许自由输入补充（最小版随 M1 交付） |
| 失败策略 | 默认失败即暂停队列并邮件通知（重试 / 跳过 / 终止由用户选择）；提交队列时可预配置自动继续 |
| 关键通知 | 「进入等待确认 / 失败」的邮件通知为 P0，其余通知 P1 |
| 记忆生成 | **提案即注入 + 用户确认**：每个任务结束后依据实现过程与用户决策生成记忆提案，立即注入队列中的后续任务；用户确认决定提案是否永久入库（注入依赖可追溯，事后否决时提示受影响任务）；用户可随时编辑已有记忆 |
| 计费模式 | **先 BYO**：用户自带 Anthropic API key；架构上预留平台统一计费 |
| 技术栈 | 全栈 TypeScript（与 Claude Code Agent SDK 天然契合） |
