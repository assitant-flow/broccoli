# Broccoli 项目文档（项目章程）

> 产品愿景见 [README](../README.md)，MVP 功能范围见 [mvp-scope](mvp-scope.md)，需求明细见 [requirements](requirements.md)，技术设计见 [design](design.md)。本文档回答：**这个项目要达成什么、怎么衡量、分几步走、有哪些风险**。

## 1. 项目概述

**Broccoli** 是一个面向个人开发者的云端 AI 开发平台：用户把一个项目的多个需求一次性提交为队列，AI 在云端沙箱中自动按序执行，用户只在需要决策时被邮件通知，最终以堆叠 PR 形式收回产出；协作过程沉淀为可确认、可编辑、可追溯的项目记忆。

- **形态**：云端 SaaS（浏览器使用，无常驻本地进程）
- **执行引擎**：Claude Code Agent SDK（容器化运行于云端沙箱）
- **核心价值**：不在 coding agent 本身，而在其上的**编排（队列/调度）、监控（仪表盘/通知）与记忆层**

解决的三个痛点（详见 README）：需求串行、人被动作调度器；多任务 = 多终端切换灾难；AI 健忘、上下文从零开始。

## 2. 目标与成功指标

### 2.1 MVP 目标

个人开发者通过浏览器接入多个 GitHub 项目，一次性提交成串需求，AI 在云端沙箱自动按序执行，只在需要决策时介入，以 PR 收回产出；项目上下文沉淀为记忆。

### 2.2 成功标准（发布判据）

用户早上提交一个项目的 5 个需求后离开，回来时**至少 4 个已完成并开出 PR**，全程无终端切换。
（「至少 4 个」以启用「失败自动继续」策略为前提；默认「失败暂停」策略下首个失败会阻塞后续队列。）

### 2.3 指标体系

| 类别 | 指标 | MVP 目标 | 说明 |
|---|---|---|---|
| 北极星 | 周均免陪跑需求数 | 建立基线 | 用户提交后**零人工介入**即完成并开出 PR 的需求数 |
| 质量 | PR 一次通过率 | ≥ 60% | 用户 review 后无需大改直接合并的比例 |
| 质量 | 验收一次达成率 | 建立基线 | 未触发回溯修复即全部达成验收标准的任务占比 |
| 效率 | 提交 → 开 PR 中位时长 | ≤ 30 分钟/需求 | 含环境准备与执行 |
| 效率 | 人工介入率 | ≤ 1 次/任务 | 等待确认次数 / 任务数 |
| 可靠性 | 任务失败率 | ≤ 10% | 环境类失败与 agent 类失败分开统计 |
| 可靠性 | 快照恢复成功率 | ≥ 99% | 等待确认后回复恢复的会话延续成功率 |
| 成本 | 空闲容器数 | 恒为 0 | 验证容器随队列复用 + 及时回收 |
| 成本 | 单任务沙箱成本 | 建立基线 | 容器分钟数 × 单价 |

**反指标（明确不追求）**：单任务极限复杂度（不做泛化「什么都能干」的 agent）、团队协作功能、任务数堆量。

## 3. 范围与版本路线

### 3.1 MVP 范围

以 [mvp-scope](mvp-scope.md) 为准（P0 = MVP 必须）。要点：

- 仅支持 **GitHub repo 项目**（沙箱文件项目降为 P1）
- 执行模型：**六阶段流水线**（规划拆解子任务与验收标准 → 开发 ∥ 测试用例并行 → 测试执行 → 验收对照 → 交付），分阶段模型推荐 + 自定义，执行画布可视
- 需求队列：项目内串行、项目间并行（单用户 2 容器并发，仅计执行中）
- 等待确认：立即快照释放容器、不占并发槽位，快照保留 24h（可配置）
- 失败策略：默认暂停 + 邮件通知，可预配置自动跳过继续（base 回退）
- 交付：堆叠 PR；关键邮件通知（等待确认 / 失败）为 P0
- 记忆：提案即注入 + 用户确认入库 + 注入依赖可追溯

### 3.2 版本路线

| 版本 | 内容 | 来源 |
|---|---|---|
| **MVP（M1–M4）** | 见 §5 里程碑 | mvp-scope P0 |
| **v1.x** | 完成通知、Issues 同步、沙箱内测试、PR 界面合并、堆叠链修复、仓库约定文件协同、沙箱文件项目、介入多轮讨论、用量统计与熔断、项目设置 | mvp-scope P1 |
| **v2** | 需求依赖图、记忆向量检索、用户级偏好记忆、记忆导出/写回仓库、本地 runner（`ExecutionTarget` 第二实现）、平台统一计费 | mvp-scope P2 / 范围外预留 |

## 4. 目标用户与差异化

**目标用户**：个人开发者——同时维护多个项目、希望把成串需求托付给 AI 而非全程陪跑的人。

**差异化三支柱**（竞品为云端 agent 平台 Devin / Factory / 后台 agent 类）：

1. **个人开发者的多项目聚焦**——竞品面向团队与订阅制；Broccoli 面向「一人维护一串项目」，BYO key 使成本贴近用量。
2. **需求队列的编排深度**——串行队列、堆叠 PR、需求间上下文传承、失败策略，把「一天托付 5 个需求」做到极致。
3. **记忆的可拥有与可迁移**——确认式记忆沉淀，未来可导出为仓库约定文件；资产属于用户而非平台锁定。

## 5. 里程碑计划

| 里程碑 | 范围 | 交付判据（DoD） | 验证方式 |
|---|---|---|---|
| **M1 单任务闭环** | 账号 + BYO key + GitHub OAuth + 创建项目 + 单需求提交 → 沙箱执行（简化流水线：规划 → 开发 → 交付，含最小确认问答）→ 开出 PR | 用真实 repo 走通全流程，确认问答可挂起并恢复 | 团队 dogfooding：每个开发自选 repo 提交 ≥ 3 个真实需求 |
| **M2 队列与完整流水线** | 多需求队列、项目内串行、项目间并行、**六阶段流水线（开发∥测试并行、测试执行、验收对照、执行画布、阶段模型配置）**、等待确认快照释放、失败策略、关键邮件通知、仪表盘总览 | 两个项目并行 + 单项目 5 需求队列跑一天；流水线路径（含 1 轮验收回溯修复）与等待确认 / 失败 / 挂起场景均有正确终态与邮件 | 按成功标准场景全流程演练（含故障注入） |
| **M3 记忆** | 任务后记忆生成 → 提案即注入 → 确认入库（批量）→ 注入后续任务 → 依赖追溯与否决提示 | 记忆全链路闭环；否决提案能看到受影响任务列表 | 连续提交 5 个关联需求，验证后续任务上下文包含前序结论 |
| **M4 体验补全** | 完成通知、Issues 同步、沙箱内测试、PR 界面合并、堆叠链修复、仓库约定文件协同 | P1 项完成，达到可邀请外部用户的状态 | 邀请 5–10 名外部个人开发者内测，收集北极星与质量指标 |

里程碑与技术的对应关系见 [design.md §14](design.md)。

## 6. 风险与应对

| 风险 | 等级 | 影响 | 应对 |
|---|---|---|---|
| Agent 执行不可控（方向跑偏、反复失败、低质量产出） | 高 | 直接打击「免陪跑」核心承诺 | 介入协议（P0）兜底决策点；PR review 为最终门槛；失败策略可配置；沙箱内测试（P1）前置拦截 |
| 堆叠 PR 维护成本（前序 PR 被 reject/大改，后序全部失效） | 高 | 用户回来看似完成实则是冲突链 | base 回退规则已定；堆叠链修复（P1）提供一键重跑；UI 引导按序合并 |
| Anthropic 官方云端产品补齐队列/记忆能力 | 中高 | 差异化空间被挤压 | 聚焦三支柱中的「多项目编排深度」与「记忆可迁移」；引擎抽象层（ExecutionTarget / agent SDK 可替换）降低单点依赖 |
| 沙箱安全事件（恶意仓库代码/prompt injection 窃取 key、盗刷） | 中高 | 用户资产损失、平台信任崩塌 | 出口网络白名单（P0）；GitHub token 最短生命周期注入；用量熔断（P1）；见 design §12 威胁模型 |
| 云成本失控（容器闲置、快照膨胀） | 中 | 单位经济模型不成立 | 容器随队列复用 + 空闲即回收（P0 验收：空闲容器恒为 0）；快照设保留期；单用户并发上限 |
| 快照恢复失败（会话/工作区状态丢失） | 中 | 等待确认的任务无法延续 | 快照 = 会话引用 + 工作区 patch 双保险；恢复失败自动降级为「重新执行该需求」并邮件告知 |
| BYO key 带来的体验割裂（用户需先去 Anthropic 开通） | 中 | 新用户转化漏斗损失 | 注册流程内嵌引导与连通性测试；架构预留平台统一计费（v2） |
