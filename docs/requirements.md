# Broccoli 需求文档（PRD）

> 来源：[README](../README.md) 愿景 + [mvp-scope](mvp-scope.md) 已收敛范围与决策。优先级定义：**P0** = MVP 必须；**P1** = MVP 应有（可裁剪）；**P2** = 后续版本。每条需求附验收标准（AC）。技术实现方案见 [design.md](design.md)。

## 0. 术语表

| 术语 | 定义 |
|---|---|
| 需求（Requirement） | 用户提交的一条自然语言任务描述，驻留在项目队列中 |
| 任务 / 执行实例（Task Run） | 一个需求的一次执行；重试产生同一需求的新执行实例 |
| 队列 | 一个项目内需求的有序集合，严格按序执行 |
| 沙箱 | 云端容器化的执行环境，容器随队列复用 |
| 记忆提案（Proposal） | 任务结束后自动生成、待用户确认的记忆条目 |
| 已确认记忆（Memory） | 用户确认入库的记忆条目，注入该项目后续所有任务 |
| 堆叠 PR | 需求 N 的分支基于需求 N-1 的分支，用户按队列顺序合并 |
| 阶段（Stage） | TaskRun 内的一段受管执行：规划 → 开发 ∥ 测试用例 → 测试执行 → 验收对照 → 交付；各阶段有独立模型、状态、耗时与产物 |
| 子任务（SubTask） | 规划阶段拆解出的具体执行单元，在后续阶段按序执行 |
| 验收标准（Criterion） | 规划生成的可核验条目；验收对照阶段逐条核对并留存证据，全部达成才可交付 |
| 执行画布（Canvas） | 单个任务阶段流水线的可视化视图（节点 / 连线 / 检查器） |
| 汇合（Join） | 并行支线全部进入终态后，流入下一阶段 |
| 快照挂起 | 进入「等待确认」保存会话快照；串行等待立即释放容器，并行等待保留至支线终态；超时未回复转「已挂起」 |
| base 回退 | 失败/挂起被跳过时，后续任务分支基于最后一个成功任务的分支 |

## 1. 用户与角色

| 角色 | 说明 |
|---|---|
| 个人开发者 | 唯一外部角色。拥有多个 GitHub 项目，提交需求队列，处理确认/失败，review 与合并 PR，管理记忆 |
| 系统（调度器/执行器/通知） | 内部角色，见 design.md；对用户表现为任务状态的自动流转 |

用户与项目为 **1:N** 关系（MVP 无团队协作）。

## 2. 核心用户旅程

```
① 注册登录 → ② GitHub 授权 + 配置 Anthropic key → ③ 创建项目（选 repo）
→ ④ 提交需求队列（可设失败策略，P1 起可临时覆盖阶段模型）→ ⑤ 离开
   系统按流水线执行每个需求：规划（拆解子任务、生成验收标准）
   → 开发 ∥ 测试用例编写（并行、互不阻塞）→ 测试执行 → 验收对照 → 交付开堆叠 PR；
   遇决策→邮件通知→用户回复→继续；验收未达成→自动回溯修复一轮；
   失败→按策略暂停或继续→邮件通知
→ ⑥ 回来：仪表盘总览 → 异常置顶处理 → 执行画布回看过程与验收证据 → review diff → 按序合并 PR
→ ⑦ 批量确认记忆提案（否决时可见受影响任务）→ ⑧ 下一次提交，记忆自动生效
```

旅程各环节对应的需求编号见 §3。

## 3. 功能需求

### 模块 A：账号与密钥

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-A1 | 邮箱注册 / 登录 / 登出 / 找回密码 | P0 |
| FR-A2 | Anthropic API key 管理：加密存储、连通性测试、更新、删除 | P0 |
| FR-A3 | GitHub OAuth 授权：最小 scope，获取 repo 读写权限 | P0 |

**AC-A1**：邮箱+密码注册后可登录、登出、找回密码；密码仅哈希存储；会话过期后需重新登录。

**AC-A2**：key 保存后明文不落库、不出现在任何日志/接口响应中；「测试连通性」按钮发起最小 API 调用并明确返回成功/失败原因；删除 key 后依赖它的任务无法启动并提示。

**AC-A3**：OAuth 后可列出用户 repo（含私有）；token 加密落库；用户可撤销授权，撤销后相关项目停止调度并提示。

### 模块 B：项目管理

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-B1 | 创建 GitHub 项目：授权后选择 repo，平台 clone 至沙箱 | P0 |
| FR-B2 | 项目列表与状态总览：当前执行需求、队列长度、最近完成 | P0 |
| FR-B3 | 项目设置：默认分支、环境变量/secrets 注入、删除项目 | P1 |

**AC-B1**：公开/私有 repo 均可创建；clone 失败时给出可读原因（无权限/不存在/网络）；重复添加同一 repo 有明确提示（拒绝或去重）。

**AC-B2**：列表页显示每项目的执行中需求、排队数、最近完成时间；状态变化到界面刷新延迟 ≤ 5 秒。

**AC-B3**：删除项目需二次确认，确认后容器立即回收、队列清空；项目记忆默认随项目删除，删除前提示可先导出（导出功能为 P2，MVP 仅提示）。

### 模块 C：需求队列

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-C1 | Web 输入需求：自然语言，一次多条，形成有序队列 | P0 |
| FR-C2 | 队列管理：调整顺序、编辑、删除、随时插入 | P0 |
| FR-C3 | 失败策略配置：提交队列时可设置（默认：失败暂停） | P0 |
| FR-C4 | GitHub Issues 同步：open issue 拉入队列，状态回写 | P1 |

**AC-C1**：支持逐条添加与批量粘贴（按行拆分）；保存即入队并显示队列位置。

**AC-C2**：对「排队中」的需求可拖拽排序、编辑、删除；对「执行中」需求可终止（转已取消）；「已完成/失败/挂起」不可编辑但可重试或重新入队。

**AC-C3**：策略枚举：`失败暂停`（默认）/ `失败自动跳过并继续`；策略随提交批次记录，可在提交时修改；策略对当次提交的整批需求生效。

### 模块 D：调度与执行

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-D1 | 项目间并行：单用户最多 2 个执行中容器，超出排队 | P0 |
| FR-D2 | 项目内串行：前一需求进入终态才启动下一个 | P0 |
| FR-D3 | 任务状态机：全状态可查询 | P0 |
| FR-D4 | agent 介入协议：结构化提问 → 等待确认 → 回答后恢复 | P0 |
| FR-D5 | 等待确认与快照：立即快照释放容器、不占并发槽位 | P0 |
| FR-D6 | 失败处理：默认暂停 + 邮件；重试/跳过/终止；base 回退 | P0 |
| FR-D7 | 任务实时输出：日志流式查看 | P0 |
| FR-D8 | 任务产出 diff：完成后查看代码变更 | P0 |
| FR-D9 | 测试执行阶段：沙箱运行全量测试并生成报告；未配置测试命令的项目自动跳过该阶段 | P0 |
| FR-D10 | 执行流水线：需求执行阶段化为 规划 → 开发 ∥ 测试用例 → 测试执行 → 验收对照 → 交付；阶段状态 / 耗时 / 产物全可查询 | P0 |
| FR-D11 | 规划阶段：读取记忆与前序提案，拆解具体子任务、生成实现计划与验收标准；未决技术选型抛出结构化确认 | P0 |
| FR-D12 | 子任务追踪：规划产出的子任务按序执行，状态与所属阶段联动可查 | P0 |
| FR-D13 | 验收标准跟踪：逐条记录达成状态与证据（日志 / diff / 测试报告锚点） | P0 |
| FR-D14 | 验收对照阶段：逐条核对验收标准；未达成项自动回溯修复一轮后重验，仍不达成转用户决策 | P0 |
| FR-D15 | 开发 ∥ 测试用例并行：两支线并行执行、互不阻塞，汇合后进入测试执行；可按项目关闭 | P0 |
| FR-D16 | 执行画布：阶段节点（状态 / 模型 / 耗时 / 产物）+ 连线 + 检查器详情；支持缩放 / 适配 / 全屏 | P0 |
| FR-D17 | 分阶段模型配置：每阶段可指定模型；平台给推荐值（静态映射 + 记忆偏好），用户可自定义（项目级默认） | P0 |
| FR-D18 | 提交队列时临时覆盖阶段模型配置（仅对该批次生效） | P1 |

**AC-D1**：同一时刻单用户「执行中」容器 ≤ 2；「等待确认」「已挂起」「排队中」不占用并发额度（验证方式：3 个项目同时活跃，第 3 个排队；2 个任务进入等待确认后第 3 个项目照常执行）。

**AC-D2**：同一项目任意时刻至多 1 个「执行中」任务；前序任务未到终态时后续任务保持「排队中」。

**AC-D3**：状态全集与转移：`排队中 → 环境准备 → 执行中 → 等待确认`（回复后恢复执行 / 超时转挂起）；终态：`完成 / 失败 / 已取消 / 已挂起`。所有状态在任务详情可查询，历史转移可追溯。

**AC-D4**：agent 提问包含问题说明 + ≥ 2 个预设选项 + 允许自由输入；任务转「等待确认」时容器已释放且邮件已发出；用户作答后任务恢复且 agent 能延续之前的进展（不重新开始）。

**AC-D5**：进入「等待确认」后 ≤ 1 分钟内完成容器处置——**串行等待**立即快照并释放容器；**并行等待**（另一支线仍执行中）容器保留至该支线进入终态后释放（槽位按容器租约计）；快照默认保留 24h（项目可配置）；快照期内回复 → 恢复成功且上下文延续；超时未回复 → 任务转「已挂起」+ 邮件通知，队列继续后续任务（base 回退）。

**AC-D6**：任务失败时默认暂停整个队列 + 邮件通知（含失败原因摘要）；用户选择「重试」→ 同一需求新执行实例；「跳过」→ 该需求标记跳过，下一需求启动且其分支 base 为最后一个成功任务的分支；「终止」→ 剩余队列转已取消。启用「失败自动跳过」策略时按策略自动执行并发邮件说明。

**AC-D7**：任务详情页日志流式呈现，端到端延迟 ≤ 3 秒；支持暂停滚动与回看全量日志。

**AC-D8**：完成后展示相对 base 分支的 diff；diff 含文件级与行级视图。

**AC-D9**：未配置测试命令 → 测试执行阶段标记「已跳过」并在画布注明原因；配置后：全量测试通过才可进入验收对照；失败 → 阶段失败，走 FR-D6 失败策略。

**AC-D10**：TaskRun 启动时自动创建 6 个阶段实例；阶段状态全集 `排队中 → 执行中 → 等待确认 → 完成 / 失败 / 已跳过`，画布与 API 均可查询；各阶段耗时、模型、产物计数随状态更新。

**AC-D11**：规划阶段产物固定包含：实现计划文档、子任务清单（≥ 1）、验收标准清单（≥ 3，每条可独立核验）；未决选型以结构化提问（选项 + 自由输入）转「等待确认」；规划阶段不修改代码文件。

**AC-D12**：子任务状态 `排队中 / 执行中 / 完成 / 已取消` 与所属阶段联动；开发阶段按子任务顺序推进，画布节点可见当前子任务序号。

**AC-D13**：验收标准状态 `已定义 → 已达成 / 未达成 / 待验证`；状态变更记录证据链接与达成阶段；画布检查器展示进度（如 2/8）。

**AC-D14**：验收对照发现未达成项 → 自动携带差距上下文回到开发阶段修复一轮 → 重跑受影响的测试执行 / 验收对照；修复轮次用尽（默认 1 轮，可配置）仍未达成 → 任务转「等待确认」，用户可选 重试 / 降级交付 / 终止；交付门禁：全部标准「已达成」或用户明确降级确认。

**AC-D15**：并行开启时，开发与测试用例两阶段同时「执行中」（各自独立 agent 会话，共享容器）；任一支线等待确认不阻塞另一支线；两支线均进入终态后自动进入测试执行；关闭并行则串行执行（开发 → 测试用例）。并行期间容器保持占用、槽位照计（见 AC-D5）。

**AC-D16**：画布展示全部阶段节点与连线；节点含状态 / 模型 / 耗时 / 产物；点击节点在检查器展示详情与验收标准；缩放 50–150%、适配视图、全屏可用；状态变化刷新 ≤ 5 秒（NFR-2）。

**AC-D17**：6 个阶段均有推荐模型；用户自定义后立即生效并在画布标注来源（推荐 / 自定义）；配置页支持恢复推荐；所选模型不在用户 Anthropic 账户可用范围时保存即告警。

**AC-D18**（P1）：提交队列入口可展开「阶段模型覆盖」面板；覆盖仅对该批次的任务生效，不改动项目默认。

### 模块 E：仪表盘与通知

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-E1 | 全局仪表盘：跨项目进度与全局状态计数 | P0 |
| FR-E2 | 异常置顶：等待确认/失败任务置顶且有视觉区分 | P0 |
| FR-E3 | 任务详情页：状态、日志、diff、对话历史 | P0 |
| FR-E4 | 关键邮件通知：进入等待确认/失败时发送 | P0 |
| FR-E5 | 完成通知与站内通知 | P1 |
| FR-E6 | 介入讨论：任务详情页与 agent 多轮对话 | P1 |

**AC-E1**：一屏展示所有项目的进度（完成/总数）、执行中/排队/等待确认/失败计数；仪表盘首屏加载 ≤ 2 秒。

**AC-E2**：含「等待确认」「失败」任务时置顶展示，与正常任务视觉区分；空异常时正常列表。

**AC-E3**：任务详情页含当前状态、实时日志、产出 diff、介入问答历史（问题、选项、用户回答）。

**AC-E4**：事件发生 ≤ 1 分钟内发出邮件；邮件含直达该任务确认操作页的一次性链接；同一任务同一状态不重复发送（防轰炸）；邮件发送失败有重试与告警。

**AC-E6**（P1）：用户可在任务详情页主动向等待中/执行中的 agent 发送补充说明，agent 响应并纳入上下文。

### 模块 F：交付

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-F1 | 堆叠 PR：每需求一个分支 + 自动开 PR（含变更说明） | P0 |
| FR-F2 | PR review 与合并：界面内查看 diff 并合并 | P1 |
| FR-F3 | 堆叠链修复：PR 被 reject/大改后基于新 base 重跑后续 | P1 |

**AC-F1**：分支命名规范 `broccoli/<序号>-<slug>`；PR 描述含变更说明与「依赖前序 PR（#N-1），请先合并」提示；需求 N 的 PR base 为需求 N-1 的分支；跳过/挂起场景 base 回退正确；PR 开出后任务标记完成。

**AC-F3**（P1）：选择某 PR 的新 base 后，可一键对受影响的后续需求发起重跑（作为新执行实例入队）。

### 模块 G：记忆系统

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-G1 | 项目记忆自动注入：执行前加载全部已确认记忆 | P0 |
| FR-G2 | 任务后记忆生成：任务终态后生成记忆提案 | P0 |
| FR-G3 | 提案即注入：提案立即对队列后续任务生效 | P0 |
| FR-G4 | 记忆确认入库：确认决定永久入库；支持批量确认 | P0 |
| FR-G5 | 记忆管理：查看、编辑、删除、禁用 | P0 |
| FR-G6 | 依赖追溯：注入记录落库；否决提示受影响任务 | P0 |
| FR-G7 | 初始项目分析：首次接入 repo 生成规范类提案 | P1 |
| FR-G8 | 仓库约定文件协同：加载合并 CLAUDE.md / AGENTS.md | P1 |
| FR-G9 | 记忆导出/写回仓库（导出 + 写回均已在 v2α 实现） | P2→实现 |
| FR-G10 | 用户级偏好记忆（跨项目注入，v2α 已实现） | P2→实现 |
| FR-G11 | 记忆检索优化（BM25-lite 关键词 + 可选向量，阈值触发 top-K 注入，v2β 已实现） | P2→实现 |

**AC-G1**：任务启动时，agent 上下文包含该项目全部「已确认且未禁用」的记忆；注入内容在任务详情可查看（可审计）。

**AC-G2**：每个任务到达终态（完成/失败）后生成 ≥ 0 条提案：完成任务生成实现/决策类；失败任务可生成教训类；提案附来源任务引用。

**AC-G3**：任务 N 的提案在任务 N+1 启动前已可被注入（不等用户确认）；确认只决定提案是否永久入库，不阻塞队列。

**AC-G4**：待确认提案按任务分组展示，支持批量全部确认/逐条确认；确认后对后续所有新任务生效（对已启动任务不追溯注入）。

**AC-G5**：记忆条目可查看、编辑（生成新版本）、删除、禁用；禁用后不再注入但历史注入记录保留。

**AC-G6**：每次注入记录「提案 → 被注入任务」的依赖；用户否决/删除提案时，列出曾注入该提案的任务（及同队列中其后的任务），并提供「重新入队」入口；系统不自动级联重跑。

### 模块 H：支撑能力

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-H1 | 凭证加密存储：Anthropic key 与 GitHub token 加密落库 | P0 |
| FR-H2 | 沙箱网络隔离：容器出口网络白名单 | P0 |
| FR-H3 | 容器生命周期管理：随队列复用、空闲/等待确认即回收 | P0 |
| FR-H4 | 用量统计与熔断 | P1 |

**AC-H1**：凭证以加密形态落库（KMS 或主密钥方案）；数据库泄露不直接导致凭证泄露；管理界面永不明文回显完整 key。

**AC-H2**：容器内仅可访问白名单端点（Anthropic API、GitHub API/git、依赖 registry——仅环境准备阶段）；执行阶段对非白名单端点的访问被拒绝且记录审计日志。

**AC-H3**：同一队列连续执行的任务复用同一容器（clone、依赖安装仅一次）；队列空闲后容器被回收；「空闲容器数 = 0」可监控验证。

**AC-H4**（P1）：按用户/任务统计 token 与容器用量；可设置用量上限，超限触发熔断（暂停新任务并通知）。

| NFR-2 | 性能 | 仪表盘首屏 ≤ 2s；日志端到端延迟 ≤ 3s；任务状态界面刷新延迟 ≤ 5s；执行画布状态刷新 ≤ 5s；关键邮件 ≤ 1min 送达 |

## 5. 安全威胁场景（NFR-1 展开）

| 威胁场景 | 后果 | 对策（P0） |
|---|---|---|
| 恶意仓库代码在容器内执行，尝试外发用户凭证 | Anthropic key / secrets 泄露 | 出口白名单；GitHub token 最短生命周期注入（仅 clone/push 窗口）；secrets 不落盘 |
| 仓库内容中的 prompt injection 诱导 agent 泄密或破坏 | 数据泄露 / 产出破坏 | 系统提示声明边界；secrets 不进入 agent 可读上下文；diff review 门槛 |
| agent 失控刷 token | 用户 API 账单暴涨 | 用量统计与熔断（P1，尽早）；单任务时长上限 |
| 容器间横向渗透 | 跨用户数据泄露 | 容器网络相互隔离，仅经出口代理访问白名单 |
| 平台数据库泄露 | 全部用户凭证泄露 | 凭证 AES-256-GCM 加密，KEK 与数据分离 |

## 6. MVP 发布检查单（端到端场景验收）

发布前以下场景全部通过：

1. **成功路径**：新用户注册 → OAuth → 配 key → 创建项目 → 提交 5 需求（自动跳过策略）→ 全部完成并开出 5 个按序堆叠的 PR → 批量确认记忆提案。
2. **等待确认路径**：任务中途提问 → 容器释放（并发不占槽）→ 邮件到达（≤1min）→ 链接直达 → 作答 → 恢复且上下文延续。
3. **失败路径**：任务失败（默认策略）→ 队列暂停 + 邮件 → 选择跳过 → 后续任务 base 正确回退并继续。
4. **挂起路径**：等待确认超时 → 任务转已挂起 + 邮件 → 队列继续 → 用户可将挂起需求重新入队。
5. **记忆路径**：连续 5 个关联需求 → 后续任务上下文包含前序提案 → 否决中间某提案 → 正确显示受影响任务。
6. **并发路径**：3 个项目同时活跃 → 并发 ≤ 2 → 第 3 个排队；2 个任务等待确认时第 3 个项目照常执行。
7. **回收路径**：全部队列空闲后，容器全部回收（空闲容器 = 0）。
8. **流水线路径**：提交 1 个需求 → 规划产出子任务与验收标准 → 开发 ∥ 测试用例并行（开发等待确认期间测试线持续推进）→ 汇合 → 测试执行 → 验收对照（含 1 轮自动回溯修复）→ 全部达成 → 开出 PR；全程各阶段模型按配置生效并在画布可见。
