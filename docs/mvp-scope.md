# Broccoli MVP 功能清单与范围边界

> 基于 README 中已对齐的架构决策收敛而成。优先级定义：**P0** = MVP 必须（缺了产品不成立）；**P1** = MVP 应有（体验完整，可裁剪）；**P2** = 后续版本。

## MVP 目标

个人开发者通过浏览器接入自己的多个项目，一次性提交成串需求，AI 在云端沙箱自动按序执行，用户只在需要决策时介入，最终以 PR 形式收回产出；项目上下文沉淀为可确认、可编辑、可追溯的记忆。

**成功标准**：用户早上提交一个项目的 5 个需求后离开，回来时至少 4 个已完成并开出 PR，全程无终端切换。（「至少 4 个」以启用「失败自动继续」策略为前提；默认的「失败暂停」策略下，首个失败会阻塞后续队列。）

## 功能清单

### 1. 账号与密钥

| 功能 | 优先级 | 说明 |
|---|---|---|
| 邮箱注册 / 登录 | P0 | MVP 用简单认证（邮箱 + 密码或魔法链接），不做 SSO |
| Anthropic API key 管理 | P0 | 用户自带 key（BYO），加密存储，可测试连通性 |
| GitHub OAuth 授权 | P0 | 获取 repo 读写权限，用于 clone 与开 PR；scope 最小化 |

### 2. 项目管理

| 功能 | 优先级 | 说明 |
|---|---|---|
| 创建 GitHub 项目 | P0 | 授权后选择 repo，clone 至云端沙箱 |
| 创建沙箱文件项目 | P1 | 不接 Git 的文件型项目（上传 / 在线创建文件，产出以文件交付）。**已移出 MVP**，MVP 仅支持 GitHub repo 项目 |
| 项目列表与状态总览 | P0 | 每个项目当前执行中的需求、队列长度、最近完成 |
| 项目设置 | P1 | 默认分支、环境变量 / secrets 注入沙箱、删除项目 |

### 3. 需求队列

| 功能 | 优先级 | 说明 |
|---|---|---|
| Web 手动输入需求 | P0 | 自然语言描述，一次可添加多条，形成有序队列 |
| 队列管理 | P0 | 调整顺序、编辑、删除、随时插入新需求 |
| GitHub Issues 同步 | P1 | 将 open issue 拉入队列作为需求来源，状态回写（issue 关联 PR） |
| 需求间依赖声明 | P2 | MVP 内一律按序执行，不引入依赖图 |

### 4. 调度与执行（核心）

| 功能 | 优先级 | 说明 |
|---|---|---|
| 项目间并行调度 | P0 | 不同项目的队列互不阻塞；**单用户默认最多 2 个容器并发执行（仅计「执行中」），超出排队；「等待确认」的任务已释放容器、不占槽位** |
| 项目内串行执行 | P0 | 同一项目严格按序：前一个完成（或进入终态）才启动下一个 |
| 云端沙箱执行环境 | P0 | 容器化运行 Claude Code Agent SDK；**容器随队列复用**：同一队列的任务共享容器与环境（clone、依赖安装每队列仅一次），队列空闲或进入等待确认即释放回收 |
| 任务状态机 | P0 | `排队中 → 环境准备 → 执行中 → 等待确认`（回复后恢复执行 / 超时挂起）；终态：`完成 / 失败 / 已取消 / 已挂起`，全状态可查询 |
| agent 介入协议 | P0 | agent 遇到需决策问题时抛出结构化提问（**预设选项 + 允许自由输入补充**），任务挂起为「等待确认」；用户回答后恢复执行。这是「只在需要决策时找人」的基础 |
| 等待确认与快照 | P0 | **进入「等待确认」即保存 agent 会话快照并释放容器（不占并发槽位）**；快照默认保留 24h（可配置），期间用户回复后重新拉起容器恢复执行；超时未回复则任务转「已挂起」，队列继续后续任务（分支 base 回退规则同失败跳过） |
| 失败处理 | P0 | **默认失败即暂停该队列**，记录错误并邮件通知，用户可选择重试 / 跳过 / 终止；**提交队列时可预配置失败策略**（如失败自动跳过并继续后续任务）；跳过时后续任务分支 base 回退至最后一个成功任务 |
| 任务实时输出 | P0 | 任务详情页实时查看 agent 的执行日志与过程 |
| 任务产出 diff | P0 | 完成后查看代码变更 diff |
| 执行流水线 | P0 | 需求执行阶段化：规划 → 开发 ∥ 测试用例 → 测试执行 → 验收对照 → 交付；阶段状态 / 耗时 / 产物全可查 |
| 规划阶段 | P0 | 读取记忆与前序提案，拆解具体子任务、生成实现计划与验收标准；未决选型抛结构化确认 |
| 验收标准与对照 | P0 | 标准逐条达成跟踪（含证据）；验收对照阶段核对，未达成自动回溯修复一轮，仍不达标转用户决策 |
| 开发 ∥ 测试用例并行 | P0 | 两支线并行互不阻塞（测试线限定测试目录防写冲突），汇合后进入测试执行；可按项目关闭 |
| 测试执行阶段 | P0 | 沙箱运行全量测试并生成报告；未配置测试命令的项目自动跳过该阶段 |
| 执行画布 | P0 | 阶段节点（状态 / 模型 / 耗时 / 产物）+ 检查器（子任务、验收标准达成列表）；缩放 / 适配 / 全屏 |
| 分阶段模型配置 | P0 | 每阶段可指定模型：平台推荐（静态映射 + 记忆偏好）+ 用户自定义（项目默认）；提交时临时覆盖为 P1 |

### 5. 仪表盘与监控

| 功能 | 优先级 | 说明 |
|---|---|---|
| 全局仪表盘 | P0 | 跨项目的总视图：各项目进度、全局任务状态计数 |
| 异常置顶 | P0 | 「等待确认」「失败」的任务置顶，与正常任务视觉区分 |
| 任务详情页 | P0 | 状态、日志、diff、对话历史（介入讨论的记录） |
| 关键邮件通知 | P0 | 任务**进入「等待确认」/ 失败**时发送邮件，含直达任务详情页的链接——这两个状态需要用户行动，是「只在需要决策时被通知」成立的前提 |
| 完成与站内通知 | P1 | 任务完成的站内 + 邮件通知；MVP 不做 Webhook |
| 介入讨论 | P1 | 在任务详情页与 agent 多轮对话修正方向（MVP 至少支持确认问答，多轮讨论可放宽） |

### 6. 交付

| 功能 | 优先级 | 说明 |
|---|---|---|
| 分支 + PR | P0 | GitHub 项目：每需求一个分支，完成后自动开 PR（含变更说明）；**采用堆叠策略**——需求 N 的分支基于需求 N-1 的分支（因项目内串行执行、工作区含前序变更），用户按队列顺序合并即可；**失败 / 挂起被跳过时，后续任务分支 base 回退至最后一个成功任务的分支** |
| 堆叠链修复 | P1 | 某 PR 被 reject 或 review 大改后，支持基于新 base 重跑受影响的后续任务 |
| PR review 与合并 | P1 | 在 Broccoli 界面查看 diff 并合并；MVP 也可引导跳转 GitHub 操作 |
| 文件交付 | P1 | 沙箱文件项目：任务产出文件在线浏览与下载（随沙箱文件项目移出 MVP） |

### 7. 记忆系统

| 功能 | 优先级 | 说明 |
|---|---|---|
| 项目记忆自动注入 | P0 | agent 执行需求前自动加载该项目全部已确认记忆作为上下文 |
| 任务后记忆生成 | P0 | 每个任务结束后，依据实现过程与用户决策生成记忆条目提案；**提案无需等待确认，立即对队列内后续任务生效** |
| 记忆确认入库 | P0 | 用户确认决定提案是否**永久入库**（供未来所有任务使用），不影响该提案已注入当前队列（见「需求间上下文传承」） |
| 记忆管理 | P0 | 查看、编辑、删除、禁用单条记忆；支持**批量确认**当日提案（避免回来后集中补确认） |
| 需求间上下文传承 | P0 | **提案即注入**：任务 N 的记忆提案立即进入任务 N+1 的 agent 上下文（增量价值在决策与理由等非代码上下文，代码变更本身由堆叠分支携带）；每次注入记录依赖（任务 ↔ 提案），用户事后否决提案时提示受影响任务、可选择重跑——MVP 为提示 + 手动重跑，不做自动级联 |
| 初始项目分析 | P1 | 首次接入 repo 时自动分析代码库，生成技术栈 / 结构 / 规范类记忆提案 |
| 仓库约定文件协同 | P1 | 加载并合并仓库内 CLAUDE.md / AGENTS.md 等约定文件，与平台记忆去重后注入 |
| 记忆检索优化 | P2 | MVP 全量注入；记忆膨胀后再做向量检索 / 相关性筛选 |
| 记忆导出 / 写回仓库 | P2 | 将平台记忆导出为 CLAUDE.md 等仓库约定文件，落实「记忆可拥有、可迁移」 |
| 用户级偏好记忆 | P2 | 跨项目的个人偏好（commit 风格等），MVP 先只做项目级 |

### 8. 支撑能力

| 功能 | 优先级 | 说明 |
|---|---|---|
| API key 加密存储 | P0 | 用户 Anthropic key 与 GitHub token 加密落库 |
| 沙箱网络隔离 | P0 | 容器出口网络白名单（仅 Anthropic / GitHub API 等必要端点）：Agent SDK 与用户 key、注入的 secrets 均在容器内，需防恶意仓库代码 / prompt injection 窃取 key 或盗刷额度 |
| 用量统计与熔断 | P1 | 按 token / 任务展示用户消耗；设置用量上限与异常熔断（防盗刷） |
| 沙箱资源回收 | P0 | 任务终态 / 队列空闲 / 进入等待确认后释放容器，控制成本 |

## v1 明确不做（范围外）

| 项 | 原因 / 位置 |
|---|---|
| 团队协作、多成员权限 | MVP 个人开发者；架构上用户与项目保持 1:N 即可 |
| 本地 runner 实装 | 仅在执行层定义抽象接口（`ExecutionTarget`），云端沙箱为唯一实现 |
| 平台统一计费 | 仅 BYO key；用量数据结构先记录，为后续计费留数据 |
| 项目内并行执行 | 串行已覆盖主要场景；并行引入 worktree 合并冲突等复杂度 |
| 需求依赖图 | 队列按序执行即可表达大部分依赖 |
| Webhook / IM 集成 | 通知止步于站内 + 邮件 |
| 记忆向量检索、用户级偏好记忆 | 见记忆系统 P2 |
| 移动端 | 响应式 Web 即可 |

## 里程碑建议

1. **M1 打通单任务闭环**：账号 + BYO key + GitHub 接入 + 单需求提交 → 沙箱执行（**简化流水线**：规划 → 开发 → 交付，含最小确认问答——自主执行不能没有「问人」通道）→ 开出 PR。不含并行测试线、验收对照与队列。
2. **M2 队列与完整流水线**：多需求队列、项目内串行、项目间并行、**六阶段流水线全量（开发∥测试用例并行、测试执行、验收对照与回溯修复、执行画布、阶段模型配置）**、等待确认快照释放、失败策略（默认暂停 + 可配置）、**关键邮件通知（P0）**、仪表盘总览。
3. **M3 记忆**：任务后记忆生成 → 提案即注入 + 依赖追溯 → 确认入库 → 注入后续任务。
4. **M4 体验补全**：完成通知、Issues 同步、测试执行、PR 合并操作、堆叠链修复、仓库约定文件协同 —— 对齐 P1 项。

## 已收敛的设计决策（原开放问题）

以下问题已于 2026-11-17 讨论收敛（含同日评审修订）：

| 问题 | 结论 |
|---|---|
| 「等待确认」容器与并发 | 进入等待确认即保存会话快照并释放容器，**不占用并发槽位**；快照默认保留 24h（可配置），超时未回复转「已挂起」，队列继续后续任务 |
| 沙箱并发上限 | 单用户默认 2 个并发容器（仅计「执行中」），超出排队；架构上可配置 |
| 失败策略 | 默认失败即暂停队列 + 邮件通知，用户可选重试 / 跳过 / 终止；提交队列时可预配置自动继续；跳过时分支 base 回退至最后一个成功任务 |
| PR 分支策略 | 堆叠 PR：需求 N 基于需求 N-1 的分支，用户按序合并；失败 / 挂起跳过时 base 回退至最后成功分支 |
| 确认问答协议 | 结构化预设选项 + 允许自由输入补充；最小版（自由文本）随 M1 交付 |
| 记忆传承机制 | 提案即注入：记忆提案无需确认即注入队列后续任务；确认决定是否永久入库；注入依赖可追溯，否决时提示受影响任务（手动重跑） |
| 关键通知 | 「进入等待确认 / 失败」邮件通知为 P0；完成通知等维持 P1 |
| 沙箱文件项目 | 移出 MVP、降为 P1；MVP 仅支持 GitHub repo 项目 |
| 执行模型（2026-11-18） | 任务执行阶段化为六阶段流水线；规划阶段拆解子任务并生成验收标准；验收未达成自动回溯修复一轮 |
| 并行测试线（2026-11-18） | 开发 ∥ 测试用例并行互不阻塞；测试线限定测试目录防写冲突；并行等待期间容器保留 |
| 分阶段模型（2026-11-18） | 每阶段可配置模型：平台推荐 + 用户自定义（项目默认），提交时可临时覆盖 |
